# Decisions

Architecture decisions are recorded here in date order. Each entry states the
context, the decision and the consequences, so a future maintainer knows why the
system looks the way it does. Author: @contributors.

## ADR-001 - Build a new platform instead of porting the existing code

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** Two in-house applications (one Node/TypeScript, one PHP) serve one department but
  must serve 32 departments and 3,000+ employees, with long-term maintenance by
  the university IT team.
- **Decision:** Build a new Spring Boot platform. Reuse the domain rules,
  database design and React screens as the specification, not the code.
- **Consequences:** No big-bang risk to the live systems; more upfront design
  work; the old applications remain the reference during the parallel run.

## ADR-002 - Java 17 baseline, JDK 21 recommended on the server

- **Date:** 2026-10-29
- **Status:** Superseded by ADR-014 (Java 21 is now the minimum)
- **Context:** The development machine ships with a Java 17 *runtime* only
  (`C:\Program Files\Eclipse Adoptium\jre-17...`). A JRE cannot compile, so the
  first `./mvnw verify` failed with "No compiler is provided in this
  environment". Spring Boot 4.1 requires at least Java 17.
- **Decision:** Compile for Java 17 so local builds and CI are reproducible;
  run on JDK 21 LTS in staging and production. A standalone Temurin JDK 21
  (`$JAVA_HOME`) is kept beside the project for building; it is
  not installed system-wide, so nothing else on the shared machine changes.
- **Consequences:** Builds must set `JAVA_HOME` to a JDK, not a JRE (see
  `DEPLOYMENT.md`, "Building"). No Java 21-only language features until the
  server is confirmed; upgrading the build target later is a small,
  documented change.

## ADR-003 - Spring Boot 4.1.2

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** The current stable release from Spring Initializr is 4.1.2.
- **Decision:** Use Spring Boot 4.1.2 with the modular starters generated by
  Initializr.
- **Consequences:** Newer major version than many tutorials; IT should review
  the release notes before handover. Standard Spring APIs keep migration to a
  later 4.x patch simple.

## ADR-004 - One database with department scoping

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** Options were one database per department, one schema per
  department, or one database with a `department_id` on department-owned rows.
- **Decision:** One database, one schema, `department_id` scoping enforced in
  services and tested negatively.
- **Consequences:** Simpler operations, backups and cross-department reporting;
  correctness depends on scope checks, which is why they are tested for every
  endpoint.

## ADR-005 - Reuse the React front end

- **Date:** 2026-10-29
- **Status:** Superseded by ADR-014
- **Context:** The existing React application already implements the screens the
  department uses.
- **Decision:** Reuse the React app, adapt its API client to the new backend,
  and keep screens visually familiar for staff.
- **Consequences:** Less UI work and easier training; the client must be cleaned
  of application-specific assumptions and reviewed for accessibility.

## ADR-006 - Server-side sessions with HttpOnly cookies

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** The existing PHP application stores a JWT in `localStorage`, which the code
  scanner flags and which any XSS can read.
- **Decision:** Use server-side sessions with `HttpOnly`, `Secure`,
  `SameSite=Lax` cookies and CSRF tokens.
- **Consequences:** Tokens are not readable by JavaScript; CSRF protection and
  session storage must be operated; no change to the old app until it is
  retired.

## ADR-007 - SSO first, local accounts as fallback

- **Date:** 2026-10-29
- **Status:** Proposed (awaits an identity-provider decision)
- **Context:** The university identity provider details are not yet known.
- **Decision:** Integrate OIDC SSO as the primary method; local accounts remain
  for the rollout and for service accounts, with a second factor for privileged
  roles.
- **Consequences:** Identity integration is a prerequisite for that switch;
  local accounts would stop being the way staff sign in once SSO is live.

## ADR-008 - Modular monolith, not microservices

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** The expected load (200 concurrent users) does not justify
  distributed systems, and the team is small.
- **Decision:** One deployable application with clear module boundaries. Split a
  module only when measurements show a need.
- **Consequences:** Simple deployment, transactions and backups; boundaries must
  be respected in code review.

## ADR-009 - Database-backed job queue for reports

- **Date:** 2026-10-29
- **Status:** Proposed
- **Context:** PDF and Word generation is CPU-heavy and must not block requests.
- **Decision:** Start with a database-backed queue and an in-process worker;
  move to a dedicated worker or broker only if the queue backs up.
- **Consequences:** No extra infrastructure at launch; queue metrics and alerts
  are required.

## ADR-010 - Development outside the web root, database copy only

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** A live departmental system and its database must not be disturbed.
- **Decision:** Build in `/opt/leave-platform`, which is not served by Apache. Use a
  separate schema `LEAVEAPP` on an Oracle Database Free instance, populated
  from a read-only export of the old data. Never point the new application at
  `legacy_leave` or `legacy_testing`.
- **Consequences:** A database administrator is required to install Oracle Free
  and create the schema; until then the skeleton cannot start.

## ADR-011 - Departments are data with immutable codes

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** The number of departments will grow and may be reorganised.
- **Decision:** Store faculties, departments and offices in tables. Codes are
  unique and immutable; display names can change; deactivation replaces
  deletion; merges record a successor.
- **Consequences:** No code changes for expansion; historical records remain
  correct after a reorganisation.

## ADR-012 - Standard build and packaging

- **Date:** 2026-10-29
- **Status:** Accepted
- **Context:** Handover to IT must not depend on this developer's machine.
- **Decision:** Maven wrapper, executable JAR, environment-based configuration,
  service definition; no Docker requirement.
- **Consequences:** Any Java developer can build with `./mvnw verify`; deployment
  fits a plain Linux or Windows server.

## ADR-013 - Oracle Database Free as the database

- **Date:** 2026-10-29
- **Status:** Accepted (supersedes the earlier MariaDB/MySQL assumption)
- **Context:** The university standardises on Oracle, and the project owner
  requires Oracle with a free licence. The data volume is small (structured
  leave records, no attachments in the database).
- **Decision:** Run on Oracle Database Free (renamed from 23ai to 26ai in 2026).
  On Windows the free build is 26ai Free
  (`oracle-ai-database-free-26ai-23.26.3.windows.x64.zip`); 23ai Free ships for
  Linux only. Schema changes are written in
  Oracle SQL (`NUMBER`, `VARCHAR2(n CHAR)`, `TIMESTAMP WITH TIME ZONE`,
  identity columns). The JDBC driver is `ojdbc11` and Flyway uses
  `flyway-database-oracle`, both published by Oracle under free-use terms and
  resolved through Maven Central. Oracle 19c/21c Express Edition remain
  compatible because the schema needs nothing newer than 12c.
- **Consequences:**
  - No licence cost while the free-edition limits hold: 2 CPU threads, 2 GB RAM
    and 12 GB of user data per database. Attachment files stay on disk, so the
    12 GB limit covers text rows only (R-16).
  - Oracle has no per-application database; the application owns a schema
    (`LEAVEAPP`). Backup and restore are therefore schema-level (`expdp`/`impdp`
    or RMAN), not whole-database copies.
  - Unquoted identifiers fold to upper case; no SQL or JPA annotation may quote
    an identifier.
  - Transparent Data Encryption is an Enterprise option and is not available in
    the free edition; encryption at rest comes from the operating system and
    encrypted backups (see `SECURITY.md`).
  - The team needs Oracle operational skills; this is recorded as R-17.
  - Switching to a paid Oracle edition later requires no code change, only a
    licence and a restart on the licensed home.

## ADR-014 - Vaadin Flow user interface, Java 21 baseline

- **Date:** 2026-10-30
- **Status:** Accepted (supersedes ADR-005 and revises ADR-002)
- **Context:** The project owner chose to build the screens in Java rather than
  reuse the existing React client. The interface must be maintainable by a Java
  developer, look like a normal internal application, and not add a second
  codebase (TypeScript, build tooling, client-side security review).
- **Decision:** Build the user interface with Vaadin Flow 25
  (`vaadin-spring-boot-starter`) and the Aura theme. Views are Java classes
  annotated with `@Route`; Spring Security's `VaadinSecurityConfigurer` owns
  login at `/login`, logout and CSRF. The JSON API remains available under
  `/api/v1` for future clients. The build target moves to Java 21, which Vaadin
  25 requires.
- **Consequences:**
  - One language and one build for the whole product; no separate front-end
    deployment step, and the reverse proxy serves the application only.
  - Every view needs an access annotation (`@AnonymousAllowed`, `@PermitAll`,
    `@RolesAllowed`); Vaadin denies an unannotated view.
  - Vaadin 25's default `anyRequest` rule is deny-all, so `SecurityConfig` must
    declare `anyRequest().authenticated()` through Vaadin's hook. Custom permit
    rules go before it. Removing that line locks out every page and API call.
  - Development mode needs Node.js 24 (already installed) and Vaadin's dev
    server (`vaadin-dev-server`, pinned in the POM because it is not managed by
    `vaadin-bom`). The first start builds a browser bundle and takes a few
    minutes; later starts reuse it.
  - The server keeps the UI state in memory for each user session; sizing and
    clustering follow Vaadin's session-replication guidance when the platform
    moves beyond one node.

## ADR-015 - Reports read through the owning module's repositories

- **Date:** 2026-11-05
- **Status:** Accepted
- **Context:** The rule in `ARCHITECTURE.md` is that a module calls another
  module's service, never its repository. A report breaks the rule in one
  direction: the leave register and the staff summary must aggregate leave,
  employee and balance rows in a single pass, and no owning service offers
  that. Routing the read through `LeaveService` would mean adding a
  register-shaped method to the class that holds the approval rules, which is
  where the drift between a screen and its export would start.
- **Decision:** `reporting/` may read the leave, identity and organisation
  repositories directly. Three things keep the boundary honest: reads only,
  never writes; the filter is the owning module's (`LeaveFilter` and
  `LeaveApplicationSpecifications`, widened to public for exactly this
  reason), so a report cannot answer a date question differently from the
  screen above it; and the aggregation that the database can do is left to the
  database (`totalsForYear` groups by employee and status) instead of loading
  rows into Java.
- **Consequences:**
  - A change to the leave filter reaches the reports automatically; a change
    to the report queries does not reach the screens.
  - `reporting/` now depends on three other modules' repository shapes, so a
    column rename breaks a report as well as a screen. The unit tests in
    `ReportServiceTest` name each row a report promises, and
    `verify-reports.py` runs the endpoints against the real database, because
    a mocked repository cannot catch a query the database refuses.
  - Reports answer for a caller's position: an HOD is fixed to their own
    department and a central administrator may name one or none. The role rule
    lives in `SecurityConfig` and the row rule in `ReportService`, so a caller
    with someone else's department number is refused rather than redirected.

## ADR-016 - A quoted reference is written by the database

- **Date:** 2026-11-06
- **Status:** Accepted
- **Context:** A help-desk ticket has to carry a short number both sides quote,
  `HD-000042`, and the cheapest way to make it unique is to derive it from the
  row's own id. That id does not exist until the insert has happened, so the
  obvious code - save the row, then fill in the number - cannot get past a
  `NOT NULL` column: the first statement *is* the insert, and it has to carry
  something. The first build of the help desk did exactly that and the server
  answered `ORA-01400: cannot insert NULL into ("LEAVEAPP"."SUPPORT_TICKET"."REFERENCE")`;
  the unit tests could not see it because the repository is mocked and a mock
  accepts any column the test hands it.
- **Decision:** the column is written by a `BEFORE INSERT` row trigger
  (`V014`), which Oracle runs after the identity value has been assigned, and
  JPA maps it `insertable = false, updatable = false` so the application never
  names the column in a statement at all. `SupportTicket#stampReference` mirrors
  the same rule in Java so the screen that just accepted a ticket can quote its
  number back without reading the row again.
- **Consequences:**
  - A number cannot be typed, edited or guessed wrong by any caller, on any
    path - platform, script or database console - because no path writes it.
  - The rule exists twice, in PL/SQL and in Java. Only the copy in the database
    reaches the table, so a drift could show a wrong number for one request and
    could never store one.
  - A rolled-back insert still consumes an id, so the numbers can have gaps.
    That is normal for a quoted reference; uniqueness, not density, is what the
    column is for.
  - The same shape was used by the profile-change request work as soon as it
    was built: `profile_reference_bi` in `V015` writes `PR-000042` from the id,
    for exactly this reason. A human-readable number derived from the id
    belongs in a trigger, not in service code.

## ADR-017 - A record correction writes only the fields it names

- **Date:** 2026-11-06
- **Status:** Accepted
- **Context:** A member of staff who spots a wrong phone number should be able
  to ask for that one correction without touching anything else on their
  record. The earlier application lost staff numbers exactly once by approving such a request as
  a full-row write: the code copied every column it was handed, the columns
  nobody had mentioned arrived as they were bound in the update statement, and
  the values that had nothing wrong with them went NULL. Oracle makes the same
  trap harder to see at the schema level, because an empty string and a
  missing value are both stored as NULL, so a blank proposed column cannot
  tell "not part of this request" apart from "proposed as empty".
- **Decision:** the request carries an explicit list of the fields it changes
  (`changed_fields`), and that list is the only statement of what will be
  written. A `CHECK` insists every named field carries a value, the service
  applies exactly the named fields, and no path exists that writes an employee
  record from a request without the list. Emptying a staff number or an
  e-mail address is deliberately not something a person can propose - it is
  the office's decision through the employee editor, and the help desk is the
  way to ask for it.
- **Consequences:**
  - The partial update cannot damage a column nobody mentioned, whichever
    column that is, because the list, not the row, decides the write.
  - The request stores no snapshot of the old values on purpose. The office
    reads the live record beside the proposal when it decides, so a correction
    made by hand in the meantime is visible at the decision, and approving
    re-checks the proposed values before writing them.
  - A value the record already holds is refused at submission with a sentence
    ("Your phone already is that number"), because a request the office cannot
    answer either way is noise in the queue.
  - One pending request per person is enforced by a unique function-based
    index, so two submissions in the same second cannot both enter the queue
    even if a screen races.

## ADR-018 - A hand-over of approving is a dated window, not a shared account

- **Date:** 2026-11-06
- **Status:** Accepted
- **Context:** When an officer is away, leave requests otherwise wait in a
  queue nobody is standing at. The earlier application coped with this by letting whoever knew
  the admin password sign in as the absent officer, so the audit trail named a
  person who was on leave - the record became a description of the credential
  used rather than of the decision taken. The platform must answer the same
  need without ever pretending one account is another.
- **Decision:** a supervisor or head of department hands a named colleague a
  dated window over one of their own approving steps (`SUPERVISOR` for the
  recommending of their direct reports, `DECISION` for their department's
  final decisions). The delegatee signs in as themself, the request moves into
  their own queue, and every trace of the act - the audit detail, the notice
  to the delegator - carries "acting for &lt;name&gt;, DL-xxxxxx". Three
  consequences were chosen deliberately:
  - **Expiry is a date comparison, not a job.** Every question the leave
    module asks carries today's date, so a window closes at midnight of its
    own accord and a future one cannot empty a queue early. Only closing a
    window *early* is an action, and it belongs to the delegator or to the
    office. The platform therefore needs no scheduler for this feature.
  - **One live window per person per step is a service rule, not a unique
    index.** An ended window keeps `ACTIVE = 1` (nobody revoked it), so any
    index keyed on live rows would reject next year's ordinary re-delegation.
    Creating a window takes a pessimistic lock on the delegator's staff row
    first, which closes the same race the index would have closed.
  - **A central administrator's authority is not delegable.** It is the
    fallback for the whole platform, including the screens that manage these
    rows; a fortnight of it would be a bigger act than any department's leave.
    What a head of department cannot cover while away is a missing head of
    department, which the organisation screen appoints.
- **Consequences:**
  - The audit trail always names the hand that pressed the button, and says
    beside it whose authority was being used. Nothing about a session, a
    password or an identity is ever transferred.
  - A `DECISION` window snapshots the department at the write, so a later
    transfer of the delegator or the delegatee cannot silently move an old
    window's authority.
  - A window is limited to `MAX_WINDOW_DAYS` (366). A step that must be handed
    over for longer than a year is a change of reporting line, and changes of
    reporting line belong on the staff record, where they are audited as such.
  - The delegatee cannot hand the authority back - giving back an authority was
    never the holder's act to do - so an office member can always close a
    window the delegator has forgotten.
  - Windows are visible from both sides on `/delegations` and read in full by
    the office at `/api/v1/admin/delegations`, so nobody has to ask a colleague
    whose requests they are currently standing in for.

## ADR-019 - A printed form proves itself with a keyed code, and fails closed without a key

- **Date:** 2026-11-10
- **Status:** Accepted
- **Context:** An approved leave form leaves the department the moment it is
  signed: it goes to a registrar, an examiner, a tender committee, somebody's
  telephone. the earlier application printed a QR on the same form, but its text was the applicant's
  name, dates, day count and status joined with pipes - a picture of what the
  paper already said. A forged sheet and a genuine one scan identically, because
  nothing checks anything. The platform needs a form that can be confirmed by a
  person who has no account, no role and no reason to be trusted with the
  applicant's record.
- **Decision:** each request carries a number the database stamps
  (`leave_reference_bi`, ADR-016, now for `leave_application` as `LV-000123`),
  and beside it the printed form carries a code: the first six bytes of
  `HMAC-SHA256(LEAVE_VERIFY_KEY, "LEAVE-VERIFY|" + reference)`, shown as twelve
  characters of `0-9a-f`, drawn by `QrGlyph` as SVG so the page needs no script
  and no image file. `GET /api/v1/reports/verify` is the only read in the
  platform that asks for no sign-in; it recomputes the code and, when the pair
  agrees, answers with what the form already states plus the status as it stands
  today. Four choices make that safe:
  - **The key has no default and no fallback.** A server that was not given
    `LEAVE_VERIFY_KEY` mints no code, refuses every check with 503, and prints the
    number in letters with a sentence saying this server cannot verify forms.
    Shipping a key in the repository would be worse than shipping none: every
    form ever printed would then be checkable - and forgeable - by anybody who
    read the source.
  - **The refusal is one sentence for every failure.** A reference that does not
    exist, a code that does not match and a pair that is badly shaped all return
    the same 404 with the same body, and the comparison is
    `MessageDigest.isEqual`, so neither the answer nor the time it takes tells a
    caller how close they got.
  - **The answer is no more than the sheet in front of the caller.** It repeats
    what the form already states - number, name, designation, department, leave
    type, dates, day count, whether it was compensatory - plus the status as it
    stands today. No reason, no remarks, no staff number, and not the names of
    the officer who recommended or decided. A verification confirms a document;
    it is not a read of a person's file, and the fields are chosen to keep that
    true rather than left to interpretation.
  - **What the paper can hold is finite, so the paper says so.** A reason may run
    to 1000 characters; a 135-by-190-millimetre form cannot. `IsoFormPage` prints
    the first `REASON_ON_PAPER` characters, stops at a whole word and adds where
    the rest is kept, because silently running out of paper mid-sentence would
    leave an officer reading a truncated claim they cannot tell from a complete
    one. The register and the screen still hold every word.
- **Consequences:**
  - The QR is a route, not a record. With `app.public-url` set it holds a URL a
    phone opens; without it the same two parts print as one short line to type,
    and both are read by the same check - so a form printed before the platform
    was given an address still verifies after it has one.
  - Verification is *today's* answer. A withdrawn or later-reversed request reads
    accordingly, which is the point: the paper is evidence that a number was
    issued, not that a decision still stands.
  - The endpoint is public and cheap, so it is the natural place for the
    sign-in-grade limits of the next security work: it counts as an unauthenticated
    read and must not become an oracle for walking the number range.
  - Printing is an office act and is audited as one (`LEAVE_FORM_PRINTED`, with
    every number that went out on that sheet), so a form circulating with a
    complaint attached can be traced to the run that produced it.

## ADR-020 - The security code is counted, kept as a digest, and drawn harder

- **Date:** 2026-11-10
- **Status:** Accepted
- **Context:** Task 37 gave the sign-in screen a code a bot has to read before it
  can touch a password, and the filter in front of it made that rule impossible
  to skip. Two things were still true of it. Nothing limited how many pictures
  one caller - or one thousand callers - could ask for, so the code was a cost
  rather than a barrier: a script that gave up on reading pictures could still
  mint sessions as fast as the server handed them out, and the public form check
  of ADR-019 had the same open door. And the answer sat in the visitor's session
  as plain text, which is harmless while nothing reads sessions and is exactly
  the thing that stops being harmless the day somebody adds a debug endpoint, a
  session-dump log or a heap profiler and does not know what is in there.
- **Decision:** keep the six characters, the `I L O 0 1` exclusions and the
  five-minute life - staff meet the same kind of code they meet elsewhere - and put
  three counts, one digest and a noisier picture behind them.
  - **One limiter, two doors.** `limit/RequestThrottle` counts knocks per key in
    a fixed window, holds at most 20,000 keys, and caps a knock at
    `allowed + 1` so that being refused cannot push the end of the window
    further away. It is a bean, not a table: it is asked about an *address*
    before it is ever asked about a session, and a stranger who has not been
    given a session yet is precisely who an address count is about. Two doors
    use it - the code picture (120 a minute) and the public form check (60 a
    minute) - and both answer `429` with `Retry-After`, because a script reads
    that word and a person does not need to.
  - **Three counts, three kinds of caller.** 120 pictures a minute per address
    bounds how fast anyone can create sessions; 40 pictures per browser bounds
    one visitor asking forever; 3 wrong answers per browser ends a script
    guessing at a picture. Guesses are counted even when there was no code to
    answer, since a script that posts sign-ins it never saw a picture for is the
    behaviour being ended.
  - **A wait outranks the password.** A spent count is not a refusal, it is a
    two-minute pause: during it the session is shown no new picture and its
    attempts are refused before the password is looked at, so the wait cannot be
    spent while it runs and a good password typed inside it tells the caller
    nothing about the account. The picture box holds a picture that says
    `Too many codes asked for. Try again in N seconds.` and the screen says why;
    a grey box invites the clicking the box exists to stop. A right code clears
    the tally and an expired wait clears itself, so a person who waits it out
    starts level, and a wrong guess by one browser never touches the next one.
  - **The session holds a digest, never the answer.** `HMAC-SHA256` under a
    random 32-byte key generated when the process starts, stored as 64 hex
    characters, compared with `MessageDigest.isEqual`, and normalised to
    trimmed capitals first so a code typed in lower case still matches. A keyed
    digest was chosen over a plain hash because the space is one code in
    32<sup>6</sup> - small enough that an unprotected hash of it is a list of
    codes in disguise. The key is deliberately not in configuration: codes live
    only as long as the sessions that hold them, so a restart retiring them
    costs nobody more than a fresh picture, and no key can be forgotten, shipped
    or leaked.
  - **The picture gets harder without breaking the one rule it lives by.** A
    hatched, skewed background, waves and specks under the characters and more of
    them drawn over, each character at its own baseline, tilt, size and colour -
    while still being **exactly one `<text>` element per character and nothing
    else written as text**. Every reader of the picture, from the tests to the
    checks under `docs/TEST-PLAN.md` to the proxy used for a browser pass, takes
    the characters out of the text elements in order; a decoration written as
    text would be read as part of a code. The box stays 220×68 because `app.css`
    pins that width on a phone.
- **Consequences:**
  - The numbers are properties (`app.sign-in.*`, `app.verify.*`) with the shipped
    defaults in `application.yml`, and they are set well above what a person at a
    desk does - nobody signs in forty times a minute - so the realistic reason to
    change one is a campus-wide NAT: if every department arrives at the platform
    through one address, 120 pictures a minute is a shared budget and belongs on
    the go-live notes in `ADMIN-GUIDE.md`.
  - A script that hammers these endpoints is now a script that has to pace
    itself. The live checks count their own knocks and wait out both windows
    before measuring them, because measuring a fixed window while another one is
    still open tells you nothing about either.
  - The counts live in one process, so a deployment with two servers behind a
    load balancer gives each its own budget and its own key. That is a reason to
    keep the platform on one instance until the multi-tenant work decides
    otherwise, and it is why the throttle is bounded in memory rather than
    pretending to be shared state.
  - `identity/LoginAttempts` still locks an *account* after five bad passwords.
    That count and these are different questions - one is about a person's
    leave record, the others about a browser and an address - and keeping them
    apart is what lets a wrong code cost nothing to the account it was typed
    against.
  - The plain-text answer is gone from the session, so the standing rule that a
    session is not a secret store now holds by construction rather than by
    careful reading of the code.

## ADR-021 - The authenticator code is checked before the password, not after it

- **Date:** 2026-11-10
- **Status:** Accepted
- **Context:** Task 49 lets an account owner add a second thing to have at
  sign-in: a six-digit code from any standard authenticator app, worked out by
  `OneTimeCodes` as RFC 6238 TOTP (HMAC-SHA1, 30-second step, one step forgiven
  either side, so up to a minute of clock skew, and deliberately not a knob to
  turn upwards). A password alone is what a phishing page, a reused login or a
  shoulder-surfed keyboard already buys an attacker. It is optional and per
  account, off until the person turns it on, because making it a condition of
  signing in would push clerks and heads of department back to the paper
  register, which is the failure this platform exists to end. The design
  question this entry answers is not whether to ask for the code but *where* in
  the sign-in to ask for it, because the same person types the security code, the
  app code and the password on one screen.
- **Decision:** check the app code before Spring Security looks at the password,
  in `config/TwoStepEnforcementFilter`, ordered after `CaptchaEnforcementFilter`
  and before `UsernamePasswordAuthenticationFilter`. Four reasons, all of them
  why the order was chosen rather than preference:
  - **The counts already shipped are what cap guessing.** Every attempt that
    reaches the code check has had to answer a security-code picture first, so
    the numbers from ADR-020 (pictures per address per minute, pictures per
    browser, three wrong answers and a 120-second wait) are the ceiling on
    guessing a six-digit number too. An enrolled account is no softer a target
    than an unenrolled one, because the same door has to be opened to reach the
    same box either way.
  - **A refusal cannot say the password was right.** A wrong code never reaches
    the password hash, so the answer cannot confirm that half of the pair. Both
    a wrong code and a wrong password send the browser to the *same* page,
    `/login?error`, with no words about which half failed. A two-screen design
    ("password accepted, now your code") necessarily announces that the password
    was correct, which hands an attacker everything a leaked password already
    gives them and more.
  - **A correct code grants nothing.** With a wrong password the attempt still
    fails: the filter only declines to refuse, it never authenticates. Whoever
    holds the phone is back at the beginning.
  - **No half-authenticated session is parked.** Checking after the password
    would need somewhere to hold a session that is in but not fully in, a second
    screen with its own limits, and a way to promote the Spring Security context
    inside Vaadin. Three things the platform does not have to get right.
  Around that order sit four further choices. A refused code is counted, in
  `TwoStepService.checkSignInCode`, into the *same* counter as a wrong password
  (`AppUser.registerFailedAttempt`, `LoginAttempts.MAX_FAILURES` 5 and
  `LOCK_DURATION` 15 minutes), so at most 5 code guesses per 15 minutes per
  account against a space of 1,000,000 a try; one number shared rather than two
  because they are the same question. The seed is stored on `app_user`
  (`V018`) as `two_factor_secret` (sealed `v1:` plus base64 AES-GCM by
  `EnrolmentCipher`) beside `two_factor_enrolled_at`, guarded by two CHECK
  constraints so the pair is either both present or both absent and a value is
  either NULL or one this platform sealed; there is no "required" column,
  because whether the second step happens is read from the presence of a seed.
  It is sealed under `LEAVE_TWOSTEP_KEY` (`app.two-step.key`), deliberately its
  own phrase and its own `EnrolmentCipher` rather than a shared `SecretCipher`
  with `LEAVE_MAIL_KEY`: one phrase covering both would mean one leaked file
  unlocks the university's outgoing mail *and* every account's second factor.
  And nothing is written on enrolment until the person types a live code that
  matches.
- **Consequences:**
  - The confirmation gate is what makes a mistyped seed impossible. Without it a
    bad seed would sit in the database looking enrolled and refuse every sign-in
    forever; with it three wrong confirmations throw the pending seed away and
    the setup must be started again, and the seed lives only in that browser's
    session (`app.two-step.seed`, `.expires-at`, `.wrong-codes`) for 15 minutes
    before then.
  - A seed must be reversible, unlike a password, because the platform
    recomputes the code from it, so the key is a genuine dependency: losing
    `LEAVE_TWOSTEP_KEY` makes every stored seed unopenable, enrolled accounts
    cannot sign in, and the log line `TWO_STEP_SEED_UNREADABLE` says so. The
    recovery is the administration team turning two-step off for the account and
    the person enrolling again. Enrolment is refused outright while the key is
    missing, so a seed is never stored in the clear.
  - Keeping `EnrolmentCipher` a separate class from `mail/SecretCipher`, with the
    same AES/GCM construction (12-byte random IV, 128-bit tag, key the SHA-256 of
    the phrase), costs a little duplication and buys the ability to rotate,
    replace and audit the two secret classes apart.
  - The two-step is per account and optional, so the sign-in screen labels the
    app-code box "Code from your app" with the placeholder "Only if you use
    two-step" and posts it as the request parameter `otp` through the same
    hidden-field trick the security code uses (`LoginView` injects hidden inputs
    named `captcha` and `otp`). A `TwoStepEnforcementFilter` that sees no code
    for an unenrolled account passes straight through.
  - Turning it off costs a re-enrolment, deliberately: the person does it on
    `/two-step` with their password *and* a live code (`POST .../off`), because
    without the code a stolen signed-in browser could quietly remove the second
    factor and leave the account looking protected when it is not. The office
    does it from the accounts list (`DELETE /api/v1/admin/accounts/{id}/two-step`,
    audited `TWO_STEP_CLEARED`) as the recovery for a lost phone, an unopenable
    seed or a leaver, but never to their own account and never to enrol anybody:
    only the person holding the phone can enrol, so there is no such endpoint.
  - `OneTimeCodes` is written in-house rather than pulled from a library because
    the platform builds offline from a local Maven repository and the standard is
    that small; the trade-off is that it is code this project owns and must keep
    correct, which is why it is pinned to the published RFC 6238 vectors.
