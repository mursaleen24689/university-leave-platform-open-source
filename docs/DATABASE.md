# Database

## Engine and conventions

- Oracle Database Free. On Windows the free build is 26ai Free
  (`oracle-ai-database-free-26ai-23.26.3.windows.x64.zip`); the 23ai free
  edition is Linux-only (RPM, container image). Oracle 19c/21c Express Edition also work; nothing
  in the schema needs a feature newer than 12c. The database character set is
  `AL32UTF8`, set once when the database is created.
- There is no per-application database in Oracle. The application's database is
  a dedicated schema owner, `LEAVEAPP`, with quota on the `USERS` tablespace.
- Table and column names are lower snake_case, singular table names where
  practical (`faculty`, `department`). Oracle folds unquoted identifiers to
  upper case, so the stored names are `FACULTY` and `DEPARTMENT`. Never quote
  an identifier in SQL or in a JPA annotation; quoting would create a second,
  case-sensitive object that no longer matches.
- Every table has `id NUMBER(19) GENERATED BY DEFAULT AS IDENTITY` as the
  primary key.
- Text columns use `VARCHAR2(n CHAR)` so multi-byte names fit regardless of the
  database character set. Never use `VARCHAR2(n BYTE)`.
- Booleans are `NUMBER(1)` with a `CHECK (col IN (0, 1))` constraint, because
  Oracle only gained a native `BOOLEAN` column type in 23ai. Hibernate 7 maps
  Java `boolean` to `BOOLEAN` and fails schema validation against such a column,
  so `NumericBooleanConverter` (auto-applied) stores them as `1`/`0` through
  `BigDecimal`. Do not remove that converter, and do not switch the columns to
  `BOOLEAN` unless support for 19c/21c Express Edition is dropped.
- Timestamps are `TIMESTAMP WITH TIME ZONE`, written in UTC (`created_at`,
  `updated_at`); calendar dates are `DATE` at midnight UTC.
- Oracle has no `ON UPDATE CURRENT_TIMESTAMP`. `updated_at` defaults to
  `SYSTIMESTAMP` on insert and is set by the application on update through the
  JPA `@PrePersist` / `@PreUpdate` callbacks on the entities that carry the
  column (`LeaveApplication`, `ProfileRequest`, `SupportTicket`,
  `ApprovalDelegation`). If a future tool writes rows without going through the
  application, add a trigger in a new migration and document it here.
- An empty string is stored as `NULL` in Oracle. Code must not rely on
  distinguishing `''` from `NULL`.
- Every department-owned table carries `department_id` with a foreign key.
- No cascading deletes on business data. Use `active` flags and explicit
  archival; foreign keys use the default (no action) behaviour.
- No stored procedures, and no triggers carrying business rules: those live in
  services and are tested. The one exception is the four `BEFORE INSERT` row
  triggers that stamp a quoted reference from the identity column (`V014` to
  `V017`, corrected by `V019`), because the id does not exist until the insert
  and the column is `NOT NULL`. See "ticket_reference_bi" below and ADR-016.
- The application schema owner has no `DROP ANY TABLE`, no `CREATE ANY TABLE`
  and no DBA role in production, so it cannot affect other schemas on the same
  Oracle instance.
- Attachments and generated documents live on the file system, not in the
  database. This keeps the data below the 12 GB Oracle Free limit.

## Migrations

- Flyway, forward-only. Files live in
  `backend/src/main/resources/db/migration`.
- Naming: `V001__create_organization.sql`, `V002__sample_reference_data.sql`.
  Never edit a migration that has run in staging or production; add a new one.
- Migrations must be idempotent where possible and safe to run on an empty
  database.
- Sample data is clearly marked with a `SAMPLE-` code prefix; `V006` replaced it
  with the official faculty and department list supplied by the university on
  2026-10-30, deleting the `SAMPLE-` rows and moving any employee parked on them
  to `ADMIN` first. No personal data is loaded by a migration: staff records
  arrive through the CSV import on the Administration screen
  (`EmployeeAdminService`), which is built. The one-off tool that migrates the
  legacy leave data is not part of this release.
- No personal data in migrations.

Transport on day one even though those units publish no staff list, and complete
the fields later.

Join table between `app_user` and `app_role`, primary key
`(user_id, role_id)`, no cascade delete.

### `password_history`

`user_id`, `password_hash`, `changed_at`. Every password change copies the old
hash here and the newest five are kept; a new password may not match the current
one or any of those five. Only hashes are stored.

## Leave tables (implemented, `V007`)

`leave_type` (code, name, `annual_allowance`, `active`; seeded with `CL`,
Casual Leave, 25 days), `leave_balance` (unique per employee, type and year,
with `allocated` and `used`; remaining is derived), `public_holiday` (one row
per date, unique) and `leave_application` (dates, server-computed `days`,
status `PENDING_SUPERVISOR`/`PENDING`/`APPROVED`/`REJECTED`/`WITHDRAWN`,
supervisor step, decision, remarks, timestamps). The rules and the deliberate
differences from the earlier application are in `LEAVE-RULES.md`.

`public_holiday` and `leave_balance` are written only through the Leave setup
screen and its `/api/v1/admin` endpoints, and every write is audited. A holiday
date is unique, so a duplicate is refused; a balance can never be corrected
below the days already `used`. Both writers - `BalanceAdminService.adjust` and
`LeaveService.deduct` - take a pessimistic lock on the **employee** row before
they look for the balance row, and only then lock the balance itself. On the
first use of a year there is no balance row to lock, so without the employee
lock two decisions taken at the same moment would both find nothing and both
try to insert one; the loser would fail on `uk_leave_balance` and the approver
would see an error for a request that was perfectly in order. The employee row
exists in both cases, so the two paths queue behind each other instead.

### `leave_balance` index (`V020`)

`uk_leave_balance` is `(employee_id, leave_type_id, leave_year)`, which serves one
person's own balances but leads with a column the year-end reports never name.
`LeaveBalanceRepository.findAllForYear` asks for every balance of a type in a
year, so `V020` adds `idx_balance_type_year` on `(leave_type_id, leave_year)`.

Measured instead of guessed, on a throwaway schema filled to the size an
installation reaches - 4,000 staff, 6 leave types, 3 years, 72,000 balance rows -
with statistics gathered before the plan was read. The register query moved from
`TABLE ACCESS FULL` on `LEAVE_BALANCE` to `INDEX RANGE SCAN` on the new index. On
a schema seeded only with the single `CL` type nothing changes: one value in that
column carries every row, so the optimizer keeps the full scan, or the
`UK_LEAVE_BALANCE` skip scan it used before.

The other index that was suggested for this table's reports, `leave_application
(leave_type_id, status)`, was measured too and **not** added: no query in the
codebase names `leave_type_id` on that table, so it would cost a write on every
request for a read that never happens.

### leave_application (V010 adds two columns, V017 adds one)

| Column | Meaning |
| --- | --- |
| `withdrawn_at` | When the applicant pulled the request back; only set on status `WITHDRAWN`. |
| `compensated` | `1` when the request was approved as compensatory leave, so `leave_balance` was not touched. |
| `reference` | The request's own number, `LV-000123`. `NOT NULL`, unique (`uk_leave_reference`, which is also how the public verification read finds the row), and **written by the database** - `leave_reference_bi` stamps it from the id in a `BEFORE INSERT` trigger, the shape ADR-016 set for reports and tickets. It is what the printed application form quotes, the number the register row shows beside the staff number, and the half of the pair an office checks against (`IsoFormPage`, ADR-019). The application maps it `insertable = false` and copies the stamped value back onto the object it hands to a screen, because a trigger writes it after Hibernate has built the row. |

`V017` adds the column, the trigger and the unique index, then backfills every
request that already existed - an old paper file gets the number its id would
have been given, so a form printed today matches a register that has been
rebuilt from the archive.

## Notification table (implemented, `V011`)

### `notification` (`V011`)

| Column | Type | Notes |
| --- | --- | --- |
| id | NUMBER(19) identity | Primary key |
| recipient_username | VARCHAR2(60 CHAR) | The account this message is for; foreign key to `app_user` with `ON DELETE CASCADE` |
| kind | VARCHAR2(40 CHAR) | A `NotificationKind` name: `REQUEST_WAITING`, `REQUEST_RECOMMENDED`, `REQUEST_WITHDRAWN`, `REQUEST_DECIDED`, or one of the help-desk kinds `TICKET_WAITING`, `TICKET_ANSWERED`, `TICKET_CLOSED` |
| title | VARCHAR2(200 CHAR) | The one line the list shows |
| body | VARCHAR2(1000 CHAR) | Who asked, over which dates, and the remarks an approver typed - never a password, a hash or a security code |
| application_id | NUMBER(19) | The row the message is about: a leave application for the `REQUEST_*` kinds, a `support_ticket` id for the `TICKET_*` kinds. A plain number rather than a foreign key, because it points a reader at a row for context and nothing in the platform deletes either kind of row. Safe to share because the kind decides which screen opens it - see `NotificationsBell.target` |
| created_at | TIMESTAMP WITH TIME ZONE | Set by the application; the list is ordered by it, newest first |
| read_at | TIMESTAMP WITH TIME ZONE | NULL until the recipient marks it read |

Indexes: `idx_notification_recipient` on `(recipient_username, created_at)` for
the list and `idx_notification_unread` on `(recipient_username, read_at)` for the
badge, which is only ever a count of rows with a NULL `read_at` for one account.

The deliberate difference from `audit_event`: that table keeps its actor as free
text so an entry still reads after the account is gone, while a message has to be
addressed to an account that can open it, so the recipient is a foreign key. A
disabled account keeps its unread messages (nothing is sent to it in the meantime,
and `LeaveNotifier` skips an account that is not enabled rather than write mail
nobody can read); an account that is deleted takes its messages with it.
`read_at` is stamped once and never changed, so marking a message read a second
time keeps the first stamp. The application only inserts rows and marks them read
- no path edits the words or deletes a message.

## Mail tables (implemented, `V012`)

### `mail_setting` (`V012`)

One row, id `1`, enforced by `ck_mail_setting_id`. The migration inserts it with
mail switched off, so the screen has something to read on a fresh database.

| Column | Type | Notes |
| --- | --- | --- |
| id | NUMBER(19) | Always 1; a second mail server would mean deciding which message went where, and nobody has asked for that |
| enabled | NUMBER(1) | The switch. Separate from "a host has been typed", so filling in the details never starts mail going out by itself |
| host | VARCHAR2(250 CHAR) | SMTP server name |
| port | NUMBER(5) | 1..65535 or NULL, enforced by `ck_mail_setting_port` |
| username | VARCHAR2(250 CHAR) | The sign-in name on the mail server, not a platform account |
| password_cipher | VARCHAR2(1000 CHAR) | `v1:` + base64 of AES-GCM over `LEAVE_MAIL_KEY`. Never a plain password, never returned by any endpoint |
| from_address | VARCHAR2(320 CHAR) | The address the mail is sent from; validated to contain `@` |
| use_tls | NUMBER(1) | STARTTLS on or off, for a relay that only speaks plain SMTP |
| mailed_events | VARCHAR2(400 CHAR) | Comma-separated `NotificationKind` names. Empty means every kind the bell shows |
| updated_by | VARCHAR2(60 CHAR) | Who saved it last, as text (the same reason `audit_event.actor_username` is text) |
| updated_at | TIMESTAMP WITH TIME ZONE | When |

Both flag columns are constrained to 0 or 1 (`ck_mail_setting_flag`), matching
the `NUMBER(1)` convention the rest of the schema uses through
`NumericBooleanConverter`.

The row is read for every message rather than cached, so a host typed at four
o'clock is used at four oh-one without a restart.

### `mail_log` (`V012`)

| Column | Type | Notes |
| --- | --- | --- |
| id | NUMBER(19) identity | Primary key |
| attempted_at | TIMESTAMP WITH TIME ZONE | Default `SYSTIMESTAMP`; the screen lists the newest 50 |
| recipient | VARCHAR2(320 CHAR) | The address asked for, or the sign-in name when there was no address |
| subject | VARCHAR2(200 CHAR) | The message title, which is the only part of the mail worth reading in a list |
| outcome | VARCHAR2(20 CHAR) | `SENT`, `FAILED` or `SKIPPED`, enforced by `ck_mail_log_outcome` |
| detail | VARCHAR2(1000 CHAR) | Why not - the mail server's own words, or the setting that stopped it. Never the password, never the body |

Index: `idx_mail_log_recent` on `attempted_at DESC`.

This is a log, not a queue: a failed message is not retried, and the in-app
message was already committed before the attempt, so nothing is lost either way.
`SKIPPED` exists beside `FAILED` on purpose - "the settings said not to mail
this kind" and "the mail server refused us" are different answers, and a table
that could only record the second would make a switched-off feature look broken.

### `ticket_reference_bi` (`V014`, corrected by `V019`)

`reference` is derived from `id`, and `id` only exists at the moment the row is
inserted. An application that inserts the row and then fills the number in a
second statement cannot get past the `NOT NULL` constraint - the first statement
is the insert and it has to carry something. So a `BEFORE INSERT` row trigger
writes it:

```sql
CREATE OR REPLACE TRIGGER ticket_reference_bi
BEFORE INSERT ON support_ticket
FOR EACH ROW
BEGIN
    :NEW.reference := 'HD-' || LPAD(TO_CHAR(:NEW.id), GREATEST(6, LENGTH(TO_CHAR(:NEW.id))), '0');
END;
```

`V019` replaced the same trigger on all four reference tables
(`leave_application`, `support_ticket`, `profile_request`,
`approval_delegation`). The original `LPAD(..., 6, '0')` does not only pad: when
the text is already longer than six characters it keeps the leftmost six and
throws the rest away, so id 1000000 was written as `HD-100000` - the reference
id 100000 already holds. The unique index would then refuse the insert, and the
platform would stop accepting new rows at the millionth with an `ORA-00001`
that says nothing about the real cause. `GREATEST(6, LENGTH(...))` makes six a
minimum width rather than a maximum, which is what the Java side
(`String.format("%06d", id)`) always meant. No stored reference changes, because
every id below a million pads to the same six digits, so no printed form, QR
picture or verification code already in somebody's hands is invalidated.

Oracle gives an IDENTITY column its value before the `BEFORE INSERT` row trigger
fires, which is what makes this work. `SupportTicket.reference` is mapped
`insertable = false, updatable = false`, so JPA leaves the column out of the
statement entirely rather than sending a NULL. `stampReference()` mirrors the
same rule in Java only so the screen that just accepted a ticket can quote its
number without reading the row back; the trigger is the only writer, so the two
could disagree about what is displayed for one request and could never disagree
about what is stored.

An insert that is rolled back still consumes an `id`, so the numbers can have
gaps. That is normal for a quoted reference and is not a fault: the ticket the
person sees is the one that was stored.

## Record-correction table (implemented, `V015`)

### `profile_request` (`V015`)

| Column | Type | Notes |
| --- | --- | --- |
| id | NUMBER(19) identity | Primary key |
| reference | VARCHAR2(20 CHAR) | The number both sides quote, `PR-000042`. `NOT NULL`, unique (`uq_profile_reference`), and **written by the database** - `profile_reference_bi` stamps it from the id in a `BEFORE INSERT` trigger, the shape ADR-016 set for tickets |
| employee_id | NUMBER(19) | Foreign key to `employee`. Whose record this is and who asked - a person proposes changes to their own record only, so there is no separate "asked by" column |
| changed_fields | VARCHAR2(200 CHAR) | Comma-separated names of the fields this request changes. This list, not the columns below, is the authoritative statement of what approving will write - Oracle stores an empty string as NULL, so a blank proposed column cannot tell "not proposed" apart from "proposed as empty". `ck_profile_changed` refuses spaces only |
| full_name_proposed | VARCHAR2(150 CHAR) | The name asked for; ignored unless `changed_fields` names `FULL_NAME` |
| employee_no_proposed | VARCHAR2(30 CHAR) | The staff number asked for; ignored unless the list names `EMPLOYEE_NO` |
| designation_proposed | VARCHAR2(100 CHAR) | The designation asked for; ignored unless the list names `DESIGNATION` |
| email_proposed | VARCHAR2(150 CHAR) | The e-mail asked for, already lower-cased; ignored unless the list names `EMAIL` |
| phone_proposed | VARCHAR2(40 CHAR) | The phone number asked for; ignored unless the list names `PHONE` |
| reason | VARCHAR2(1000 CHAR) | Why the person wants the change; written by them, read by the office |
| status | VARCHAR2(20 CHAR) | `PENDING`, `APPROVED`, `REJECTED` or `CANCELLED`, enforced by `ck_profile_status`. A person withdrawing their own request lands it in `CANCELLED`, which is why four states exist where the office's answer has two |
| decided_by_employee_id | NUMBER(19) | Foreign key to `employee`. The office member who approved or refused - or the person who withdrew it; NULL while `PENDING` |
| decision_note | VARCHAR2(1000 CHAR) | What the office said about its decision. Required when refusing, so a refusal can be acted on; the person reads these exact words |
| created_at | TIMESTAMP WITH TIME ZONE | Set by the application |
| updated_at | TIMESTAMP WITH TIME ZONE | Set by the application on every change |
| decided_at | TIMESTAMP WITH TIME ZONE | When the request stopped being pending |

There are deliberately no "current value" columns: the office reads the live
record beside the proposal when it decides, so a correction made by hand in the
meantime cannot be approved against a snapshot that no longer exists.

`ck_profile_named` insists that every field named in `changed_fields` carries a
value in its column. A request therefore cannot say "remove my phone number" -
emptying a staff number or an e-mail is the office's decision on the employee
record, not something a person can propose at a keyboard.

`ck_profile_decided` ties `decided_at` and `decided_by_employee_id` to the
status being anything but `PENDING`, for the same reason `ck_ticket_closed`
exists: a list must never show a decided row with no decision behind it.

Indexes: `idx_profile_employee` on `(employee_id, created_at)` for a person's
own history, and `idx_profile_status` on `(status, created_at)` for the office
queue, which is read oldest first. A unique function-based index
`uq_profile_one_pending` on `(CASE WHEN status = 'PENDING' THEN employee_id
END)` lets one person have exactly one waiting request: it is NULL for every
row already decided, Oracle keeps no entries for an all-NULL key, and the
application turns the clash into a readable sentence before the constraint is
reached - the index is there so two submissions in the same second cannot both
enter the queue.

## Handover table (implemented, `V016`)

### `approval_delegation` (`V016`)

| department_id | NUMBER(19) | For `DECISION`, the department whose decisions are covered, snapshotted when the window is written so a later transfer cannot move the authority with the person. `ck_delegation_department` insists it is set for `DECISION` and NULL for `SUPERVISOR`, because a recommending window reaches its requests by the supervisor's name, not by department |
| start_date | DATE | First day the delegatee may act |
| end_date | DATE | Last day they may act; `ck_delegation_dates` refuses an earlier last day than the first. The window closes after it with nobody having to remember - expiry is a date comparison, not a job (ADR-018) |
| reason | VARCHAR2(1000 CHAR) | Why the hand-over is needed, in the delegator's words; read by the colleague and by anyone auditing a decision |
| active | NUMBER(1) | `0` or `1`, enforced by `ck_delegation_active`. It means *revoked or not*, nothing else: an ended window keeps `1` and is excluded by its `end_date`, so the usable set is `ACTIVE = 1` plus the window covering today |
| revoked_by_employee_id | NUMBER(19) | Foreign key to `employee`. Who closed the window early - the delegator or the office, never the holder |
| revoked_at | TIMESTAMP WITH TIME ZONE | When it was closed early |
| created_at | TIMESTAMP WITH TIME ZONE | Set by the application |
| updated_at | TIMESTAMP WITH TIME ZONE | Set by the application on every change |

`ck_delegation_revocation` keeps `active` and the two revocation columns in step
in both directions, so a list can never show a closed window with no name and
no date behind it, nor a live one carrying them.

There is deliberately **no unique index for one live window per person per
step**. A window that ended last month still has `ACTIVE = 1` - nobody revoked
it - so an index keyed on the live rows would reject this year's fresh window,
which is the ordinary thing a head of department does annually. The service
refuses the second window instead, after taking a pessimistic lock on the
delegator's staff row, the same protection an approval uses on the record it is
about to write.

Indexes: `idx_delegation_from` on `(from_employee_id, start_date)` for the
conflict check and the delegator's own list, and `idx_delegation_to` on
`(to_employee_id, active, end_date)` for the question the queues ask every
time - which windows is this person standing in for today.

## Planned tables (Phases 2 and 3)

`leave_entitlement`, `leave_status_history`, `holiday`,
`holiday_department`, `attachment`, `job_queue`.

Design rules for these tables:

- `leave_application.department_id` records the department at application time,
  even if the employee later transfers.
- `leave_status_history` is append-only and is the source of truth for the
  approval timeline.
- `audit_event` is append-only at the application level: no update or delete
  path exists, and the detail column never holds a secret.
- Attachments store metadata only; file content lives in storage with a random
  name and a checksum.

## Department lifecycle

Adding a department:

```sql
INSERT INTO department (faculty_id, code, name, department_type, active)
VALUES (:facultyId, :code, :name, 'ACADEMIC', 1);
```

Renaming changes `name` only; `code` is never reused. Deactivation sets
`active = 0` and hides the department from new employee records and new leave
applications while preserving history; activation sets it back. Both directions
are administrator functions with an audit event, on the Administration screen
and at `PUT /api/v1/admin/departments/{id}/active`.

Two parts of the lifecycle are modelled but not yet reachable by an
administrator. `OrganizationAdminService.renameDepartment` exists and is unit
tested, but no controller endpoint and no button call it, so a rename today is a
service-layer operation only. A merge would set `successor_id` on the retired
department and let reporting follow the successor chain; the column exists
(`V001`) and nothing writes it, so merging is **planned, not built**. Faculties
have the same active flag and the same both-directions endpoint,
`PUT /api/v1/admin/faculties/{id}/active`; closing a faculty does not close the
departments under it, and reopening it does not reopen them.

## Provisioning the schema

A DBA connects to the `FREEPDB1` pluggable database and creates one schema
owner. Nothing else on the instance is touched.

```sql
CREATE USER LEAVEAPP IDENTIFIED BY "<strong-password>"
  DEFAULT TABLESPACE USERS QUOTA UNLIMITED ON USERS;

GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE, CREATE VIEW,
      CREATE PROCEDURE, CREATE TRIGGER, CREATE TYPE TO LEAVEAPP;
```

The application then needs only `LEAVE_DB_URL`, `LEAVE_DB_USER` and
`LEAVE_DB_PASSWORD`. Flyway creates its history table and then the application
tables inside that schema.

To undo everything for this application, a DBA runs `DROP USER LEAVEAPP
CASCADE`. Other schemas are unaffected.

## Backup

This platform runs on Oracle, so there is no `mysqldump` and no
`--single-transaction`. The two honest options are a Data Pump export of the
schema or an RMAN backup of the database:

- Logical: `expdp` of the `LEAVEAPP` schema, nightly, copied off the server.
  This is what a deployment of this size wants: it is one schema, it can be
  imported into a scratch schema for a restore drill without touching anything
  else, and it does not need the DBA to hand over the whole instance. The
  procedure and the privileges it needs are under "Backup and restore" below.
- Physical: RMAN, which is present in Oracle Database Free and backs up the
  whole database rather than one schema. It is a DBA operation run as
  `SYSDBA`, not something the application account can do, and it is the right
  choice only if the university already runs RMAN for its other databases and
  wants this instance inside that schedule.
- Encryption has to happen outside the database on this edition. Data Pump
  dump-file encryption (`ENCRYPTION=ALL`) and RMAN backup encryption are both
  part of the Oracle Advanced Security option, which is an Enterprise Edition
  feature and is not available in Free. Encrypt the dump file with the backup
  tooling or the operating system before it leaves the server, and keep the key
  with the team secret store, not beside the file.
- Test restore into a scratch schema once a month; a backup that has never been
  restored is not a backup.
- Never back up or restore the database by copying data files while the
  instance is running.
- No backup script is committed yet. `ops/README.md` lists `backup/` and
  `restore/` as planned contents; until they exist the commands below are run
  by hand or by the university's own scheduler.

## Migration from the earlier application

1. A database administrator takes a read-only dump of the legacy schema.
2. Import into `leaveapp_staging`; never into the legacy schema.
3. Map legacy users to `employee_no` and department codes.
4. Reconcile counts: users, applications, balances, holidays.
5. Record discrepancies and decisions in the migration report.
6. Only after sign-off, load production through the same tool.

## Backup and restore

Data Pump writes its files on the **database server**, through a directory
object, so the setup is a DBA act done once. The path below is an example; it
must exist on the database host and be writable by the Oracle software owner.

```sql
-- As a DBA, connected to FREEPDB1.
CREATE OR REPLACE DIRECTORY LEAVE_BACKUP AS '/var/backups/app-leave';
GRANT READ, WRITE ON DIRECTORY LEAVE_BACKUP TO LEAVEAPP;
```

Exporting one's own schema needs no role beyond `CREATE SESSION` and that
directory grant. Exporting somebody else's schema, or the whole database, needs
`DATAPUMP_EXP_FULL_DATABASE`, which the application account deliberately does
not have.

```bash
# Nightly, on the database host. The password comes from the secret store,
# never from a shell history or a committed file.
expdp LEAVEAPP@//127.0.0.1:1521/FREEPDB1 \
  DIRECTORY=LEAVE_BACKUP \
  DUMPFILE=leaveapp_%U.dmp LOGFILE=leaveapp_exp.log \
  SCHEMAS=LEAVEAPP
```

`FLASHBACK_TIME=SYSTIMESTAMP` may be added for a single consistent point in
time; it reads undo, so it needs enough undo retention for the length of the
export. Without it the export is still usable, but rows changed during the run
may be captured at different moments.

The restore drill imports into a separate schema, which needs
`DATAPUMP_IMP_FULL_DATABASE` and a DBA to create the target user:

```bash
impdp system@//127.0.0.1:1521/FREEPDB1 \
  DIRECTORY=LEAVE_BACKUP DUMPFILE=leaveapp_%U.dmp \
  REMAP_SCHEMA=LEAVEAPP:LEAVEAPP_RESTORE_TEST \
  LOGFILE=leaveapp_imp.log
```

- Retention: 30 daily, 12 monthly, 7 yearly, or as IT policy requires.
- Quarterly restore into an isolated schema, verify row counts and checksum a
  sample of tables, then drop the test schema. `OPERATIONS.md` holds the drill
  step by step.
- Credentials for backups are separate from the application account, and the
  application account cannot delete the copies once they are off the server.
- A dump holds staff names, e-mail addresses and password hashes. Encrypt it
  before it leaves the server (see "Backup" above for why the database cannot
  do that itself on Free), and never commit one: `database/README.md` forbids a
  production dump or personal data in that directory.

## Reporting queries

- Read-only reporting uses dedicated queries or views; no ad-hoc SQL from the
  application user.
- Large exports run in the background queue and are limited by date range.
- Every reporting query has an index review before release; the load test
  covers the top ten.
